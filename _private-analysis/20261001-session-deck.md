## 1장 · 요약 — SAP 재고 조회 프로그램을 AI로 만들었습니다

**결론부터 — 사람이 8일 걸릴 일을 4시간 30분에 끝냈습니다**

| 사람이 직접 만들면 | 이번 AI 작업 | 차이 |
|---|---|---|
| **65시간** | **4시간 30분** | **약 14배** |
| 약 8일치 일거리 (추정) | 실제 작업 시간 (실측) | 빠르게 끝났습니다 |

- **만든 것** — 재고 현황을 단계별로 펼쳐보는 조회 화면 1개 (`ZMM_STOCK_TREE01`)
- **규모** — 프로그램 1,479줄 + 설명 문서 약 3,000줄 + 화면 그림 3장
- **진행 기간** — 이틀. 다른 업무와 병행했고, 실제 작업 시간만 4시간 30분
- **오류** — SAP에 넣은 뒤 발견된 오류 5건, 모두 해결 완료

> AI는 SAP에 접속하지 않습니다. 설계·코드·문서는 AI가 만들고, SAP 입력과 테스트는 사람이 했습니다.

**발표 노트**: 이 수치는 '사람을 대체한 배수'가 아니라 '역할을 나눈 결과'입니다. 65시간은 추정값, 4시간 30분은 실측값입니다.

## 2장 · 진행 방식 — 묻고 답하며 5단계로 진행했습니다

**코드부터 쓰지 않았습니다. 확인된 것만 코드에 넣었습니다**

| | 단계 | 내용 |
|---|---|---|
| 1 | 무엇을 만들지 묻기 | 질문 26개를 주고받았습니다. 모른다고 답한 6개는 추측값으로 메우고 '추정'이라고 표시했습니다 |
| 2 | 화면 그림을 먼저 확인 | 코드를 쓰기 전에 화면 그림을 그려 보여드리고 확인받았습니다. 합계 계산 방식도 3가지 안을 비교해 골랐습니다 |
| 3 | 실제 항목명 확인 | 확인용 작은 프로그램을 먼저 만들어 드렸습니다. 재고 테이블 7개를 직접 조회해 항목명 24개를 확정했습니다 |
| 4 | 전체 코드 작성 | 1,479줄을 한 번에 받아 SAP에 붙여넣었습니다. 주석은 한국어와 영어를 함께 달았습니다 |
| 5 | 오류 고치고 화면 만들기 | 9번 주고받으며 오류 5건을 고치고, SAP 화면·버튼·라벨 정의를 받았습니다 |

> **핵심 — 모르는 것을 추측해서 코드에 넣지 않았습니다.**
> 확인용 프로그램을 먼저 돌린 덕분에, 추측으로는 알 수 없는 4가지를 미리 걸러냈습니다 — 없는 항목 2건, 수량이 두 번 더해질 위험 1건, 금액 계산식 1건.

1~3단계는 첫째 날, 4~5단계는 둘째 날에 진행했습니다.

## 3장 · 수치 — 숫자로 보면

**주고받은 43번 중 72%는 제대로 진행된 대화였습니다**

### 주고받은 횟수 43번

| 구분 | 횟수 | 비중 |
|---|---|---|
| 제대로 진행 | 31번 | 72% |
| 오류 고치기 | 5번 | 12% |
| AI가 빠뜨려 다시 요청 | 4번 | 9% |
| 헛턴 (다시 출력 요청 등) | 3번 | 7% |

**오류 5건이 나온 곳** — 5건 중 3건이 '화면에 표를 펼쳐 보여주는 기능'의 사용법을 알아내는 과정에서 나왔습니다.

### 만든 것 · 다룬 범위

| | | |
|---|---|---|
| 프로그램 | **1,479줄** | 이 중 주석이 25% |
| 설명 문서 | **약 3,000줄** | 화면·항목 정의 포함 |
| 화면 그림 | **3장** | 미리 보여드린 것 |
| 조회 테이블 | **11개** | 항목 24개 직접 확인 |
| 실행 결과 | **재고 69만 건** | 화면에는 7,339줄 |
| 저장한 교훈 | **7건** | 다음 작업에 자동 반영 |

> 되돌아간 12번(28%) 중 4번은 AI가 'SAP 화면에서 손으로 만들 부분'의 입력값을 표로 주지 않아 생긴 것입니다. 규칙에 추가해 막았습니다.

## 4장 · 결론 — 시간 비교와 배운 점

**선행 투자가 끝났으므로, 다음 프로그램은 더 빨라집니다**

### 같은 프로그램을 만드는 데 걸리는 시간

| 구분 | 시간 | 성격 |
|---|---|---|
| 사람이 직접 (AI 없이) | **65시간** | 추정 · 범위 40~100시간 |
| 이번 AI 작업 | **4시간 30분** | 실측 · 이틀에 걸쳐 병행 |
| 같은 것을 다시 만들면 | **3시간** | 추정 · 교훈 7건이 이미 반영됨 |

65시간 산정 내역: 요구사항 확정 6h + 기존 화면 분석 6h + 항목 조사 6h + 설계 4h + 코딩 16~24h + 화면 기능 8h + 화면·라벨 작성 3h + 테스트 8h + 문서 4h

### 배운 점

1. **모르는 것은 먼저 확인했습니다** — 가장 위험한 것은 오류가 아니라 '오류 없이 조용히 틀린 숫자'입니다. 확인용 프로그램 1개로 막았습니다.
2. **되돌아간 4번은 원인이 하나였습니다** — SAP 화면에서 손으로 만드는 부분의 입력값을 표로 주지 않았습니다. 규칙에 넣어 다시 생기지 않게 했습니다.
3. **세 번째 프로그램부터 본격적인 이득입니다** — 규칙과 교훈을 쌓는 초기 투자가 끝났습니다. 반복할수록 시간 차이가 커집니다.

> **주의** — 65시간은 통상 생산성 기준의 추정값입니다. 사내 유사 개발 실적이 있으면 그 값으로 바꿔야 정확합니다. 대기·협의·승인·이송 시간은 포함하지 않은 순작업 기준입니다.

## 예상 질문과 답

| 질문 | 답 |
|---|---|
| "65시간은 어떻게 나온 숫자인가?" | 9개 작업으로 나눠 추정했습니다(4장 산정 내역). 코딩 부분은 통상 생산성 40~60줄/시간을 보수적으로 적용했습니다. **사내 실적 데이터로 교체하면 정확도가 올라갑니다.** |
| "AI가 틀린 코드를 주면?" | 이번에도 오류 5건이 나왔고 모두 사람이 SAP에서 발견했습니다. **AI 산출물은 검증 전 초안입니다.** 다만 고치는 데 1건당 5~20분이 걸렸습니다. |
| "AI가 SAP에 직접 접속하는가?" | 접속하지 않습니다. 접속 정보를 요구하지도 않습니다. 코드를 받아 붙여넣고 실행하는 것은 전부 사람의 몫입니다. |
| "재고 숫자가 틀릴 위험은?" | 가장 큰 위험이었습니다. 수량이 두 번 더해질 수 있는 지점을 확인용 프로그램으로 미리 찾아 제거했습니다. 다만 **권한 설정 1건과 금액 계산 방식은 아직 실제 검증 대기 중**입니다. |
| "다른 프로그램에도 쓸 수 있는가?" | 조회성 리포트에는 바로 적용 가능합니다. 저장·전송이 들어가는 프로그램은 검증 절차를 더 늘려야 합니다. |
