## 1. 먼저 — 지금 가진 데이터와 공백

목차를 짜기 전에 **3조건 중 하나는 아직 측정되지 않았다**는 점을 분명히 해야 한다. 이걸
모르고 목차를 짜면 발표 당일 Q&A에서 무너진다.

| 조건 | 정의 | 현재 데이터 | 상태 |
|---|---|---|---|
| **① AI 미활용** | ABAP 경력 3~5년 개발자 1명이 수작업으로 동일 산출물 제작 | 65 man-hour (범위 40~100h), 9단계 분해 산정 | **추정** — `20261001-session-analysis.md` §7.3 |
| **② 기본 AI** | 저장소(SKILL·HARNESS·practice) 없이 일반 AI 채팅에 요구사항만 주고 제작 | **없음** | **미측정 — 발표 전 반드시 확보** |
| **③ 저장소 기반 AI** | 현 저장소 하네스 적용. 인터뷰 → Gate U/D/F → Gate 2 → Gate 3 → Verify | 커밋 기준 실작업 4시간 34분 / 43턴 / 1,479행 | **실측** — 세션 기록 전수 |

### 1.1 ② 를 다른 데이터로 대체하면 안 되는 이유

저장소에는 비슷하게 생긴 비교 기록이 하나 더 있다 — `cursor/parity-scoring-guide-fe99` 브랜치의
`docs/report/parity-score-A-vs-B-2026-08.md` (통합 운영 모니터 `Y_OPS_MONITOR_V2`, 세션 A vs B).
결과는 **최종 품질 A=60 / B=61 (만점 62, 둘 다 PASS)** 이고 과정 비용만 `Q_user 63 → 16`,
`E_compile 18+ → 2` 로 갈렸다.

이 기록은 **방법론으로는 그대로 쓸 수 있지만, ② 의 실측값으로는 쓸 수 없다.**

| 문제 | 내용 |
|---|---|
| 과제가 다르다 | 운영 모니터(SM37/ST22/SXI 대시보드) ≠ 재고 트리. 발표에서 "재고조회 트리로 비교"라고 말한 것과 어긋난다 |
| A가 "기본 AI"가 아니다 | A는 스킬 체계를 **만들어 가면서** 진행한 세션이다. 저장소 없는 맨바닥이 아니다 |
| 시점이 다르다 | 2026-08. 모델·저장소 상태가 모두 다르다 |

→ **결론: ② 는 재고 트리 과제로 새로 1회 재현 측정해야 한다.** 측정 절차는 아래 §6에 적었다.

### 1.2 이 비교에서 가장 중요한 사실 (목차 설계를 지배하는 제약)

A vs B 기록이 알려 주는 것은 **"최종 품질은 수렴한다"** 는 것이다. 왕복을 충분히 하면
기본 AI도 결국 비슷한 점수에 도달한다 (A=60 / B=61, Δ=1).

따라서 **"저장소를 쓰면 더 좋은 코드가 나온다"는 주장은 세우지 말아야 한다.** 그 주장은 Q&A에서
"그럼 그냥 몇 번 더 물어보면 되는 거 아닌가"로 반박되고, 실제로 반박이 맞다.

세울 수 있는 주장은 세 가지다.

| # | 주장 | 축 | 증거 |
|---|---|---|---|
| 1 | 같은 품질에 도달하는 **왕복·오류 비용**이 다르다 | 비용 | `Q_user 63→16`, `E_compile 18→2`, 첫 PASS `Q57→Q12` |
| 2 | **"코드가 있다"와 "동작한다"는 다르다.** 기본 AI는 1턴에 완성처럼 보이는 소스를 내지만 실제 점수는 FAIL이다 | 신뢰 | Hard Gate: 코드-only 천장 44/62. B의 Q=1 산출물 = 30/62 FAIL |
| 3 | 추측으로는 맞힐 수 없는 DDIC 사실이 있고, 틀리면 **덤프가 아니라 조용히 틀린 수량**이 된다 | 위험 | `MSKU`·`MSLB` 보류 필드 부재, `MARD`/`MKOL` 이중 계상 |

**3번이 발표의 클라이맥스다.** 1번(속도)은 청중이 이미 믿고 있고, 2번은 흥미롭지만 기술적이다.
3번은 "재고 수량이 조용히 틀린다"는 업무 리스크라서 의사결정권자에게 유일하게 꽂힌다.

### 순서에 대한 설명 (이 배치를 고른 이유)

- **10장(품질 수렴)을 11장(숨은 결함) 바로 앞에 둔 것이 핵심 장치다.** 10장에서 "품질은
  비슷해진다"고 스스로 김을 빼면 청중은 "그래서 저장소가 왜 필요한가?"를 속으로 묻게 되고,
  11장이 그 질문의 답이 된다. 10장을 빼거나 뒤로 미루면 11장이 "그냥 자기 자랑 하나 더"가 된다.
- **3장(측정 규칙)을 앞에 둔 것**은 원칙 1·3 때문이다. 이 발표의 최대 리스크는 "65시간은 어디서
  나온 숫자냐"이고, 그 공격을 1.5분으로 미리 막는다.
- **6→7→8 순서로 ①②③ 를 차례로 둔 것**은 난이도 역순이 아니라 **청중의 기대를 따라간 것**이다.
  ①에서 "65시간"에 놀라고 → ②에서 "AI 쓰면 되네"로 안심하고 → ③에서 "②는 아직 끝난 게 아니었다"로
  뒤집는다. 세 장 모두 **같은 4줄 레이아웃**(진행 방식 / 왕복·시간 / 오류 / 산출물 상태)으로 고정한다.
- **12장(장치)을 비교 뒤에 둔 것**은, 장치 설명을 먼저 하면 "방법론 소개 발표"가 되기 때문이다.
  결과를 먼저 보여 주고 원인을 설명하는 순서가 설득력이 높다.

## 4. 장별 내용 설계

### 1장 · 결론

표 하나로 끝낸다. 라벨(`실측`/`추정`)을 반드시 칸 안에 넣는다.

| 지표 | ① AI 미활용 | ② 기본 AI | ③ 저장소 AI |
|---|---|---|---|
| 1건 소요 | 65h `추정` | `측정 예정` | **4.6h** `실측` |
| 사용자 왕복 | — | `측정 예정` | 43턴 `실측` |
| 활성화 오류 | — | `측정 예정` | 3건 `실측` |
| 실행 오류 | — | `측정 예정` | 2건 `실측` |
| 최종 품질 | 기준 | `측정 예정` | 동급 `실측` |
| 숨은 결함 (추측 DDIC) | 조사로 제거 | `측정 예정` | **0건** `실측` |

맨 아래 한 줄: "AI는 SAP에 접속하지 않는다. 설계·코드·문서는 AI, SAP 입력과 테스트는 사람이 했다."

### 3장 · 측정 규칙

두 축을 왼쪽·오른쪽으로 나눈 1장.

| 품질축 — 채점표 | 비용축 — 과정 효율 |
|---|---|
| 항목별 0/1/2 + 증거코드(`C` 소스검수 / `R` SAP 실기 / `A` 활성화 / `D` 설계서 대조) | `Q_user` 사람 메시지 수 |
| 차단 결함(Hard Gate): 활성화 실패·빈 화면·필수 조회 버그가 있으면 총점과 무관하게 PASS 불가 | `E_compile` 활성화·문법 오류 첨부 횟수 |
| **코드-only 천장**: 활성화·실기 증거 없으면 상한 44/62 | `E_runtime` 덤프·빈화면 등 실기 증상 횟수 |
| 판정: ≥55 PASS / 46~54 PARTIAL / ≤45 FAIL | 소요 시간 (커밋 기준 실작업) |

한 줄 강조: **"질문 수는 효율이지 품질 점수가 아니다."**

### 5장 · 왜 이 과제인가

"쉬운 과제로는 3조건이 갈리지 않는다"를 4개 사실로 보여 준다. 이 4건은 실제로
**추측으로는 맞힐 수 없었던 것**이다 (분석 §4.5).

| 항목 | 실측 결과 | 추측했다면 |
|---|---|---|
| `MSKU` (고객 특별재고) | **보류 필드 없음** | 없는 필드로 SELECT → `DBIF_RSQL_INVALID_RSQL` 덤프 |
| `MSLB` (공급업체 보유) | **보류 필드 없음 + `LGORT` 키 없음** | 저장위치 조건 입력 시 조회 결과 왜곡 |
| `MARD` 위탁 필드 | `KLABS`·`KINSM`·`KEINM`·`KSPEM` 존재 | `MKOL`과 **이중 계상** → 수량이 두 번 더해짐 |
| `MBEW` 평가 | `LBKUM`·`SALK3`, `BWTAR = space` | 평가액 계산식 오류 → 금액 전체 오차 |

덧붙일 난이도 요인: 재고 테이블이 7개로 갈라짐(`MARD`·`MSKA`·`MSPR`·`MSKU`·`MKOL`·`MSLB` + `MBEW`),
특별재고 참조 키가 테이블마다 다름(`VBELN+POSNR` / `PSPNR` / `KUNNR` / `LIFNR`),
`CL_GUI_ALV_TREE` API 관례가 클래스 내부에서도 갈라짐.

### 6~8장 · 조건별 1장 (레이아웃 고정)

세 장을 **똑같은 틀**로 만든다. 다른 건 숫자뿐이어야 한다.

```
[조건 이름]
──────────────────────────────
진행 방식    : (3~5줄 흐름)
왕복 · 시간  : Q_user / 소요
오류         : E_compile / E_runtime
산출물 상태  : 채점표 점수 + 등급 + 차단 결함
──────────────────────────────
한 줄 평
```

- **6장 (①)**: 9단계 산정 내역을 그대로 노출한다 — 요구사항 6h + 기존 트랜잭션 분석(MMBE·MB52) 6h +
  DDIC 조사 6h + 설계 4h + 코딩 16~24h + ALV 트리 구현 8h + Dynpro·상태·텍스트 3h + 테스트 8h +
  문서 4h = 61~79h. 한 줄 평: **"대부분이 코딩이 아니라 조사·설계 시간이다."**
- **7장 (②)**: 측정 후 채운다. 예상되는 모습은 "1턴에 1,000줄 넘는 소스가 나오지만 활성화하면
  오류, 특별재고 테이블은 추측, 화면 정의서 없음". 한 줄 평 후보: **"빠른 건 코드지, 완성이 아니다."**
- **8장 (③)**: 게이트 흐름을 보여 준다 — 인터뷰(I-0~I-8, 26문항) → Gate U 이해도 → Gate D 화면 이미지
  컨펌 → Gate F 필드맵 + **DDIC 점검 리포트 선행 실행** → Gate 2 스펙 → Gate 3 코드 → Verify.
  한 줄 평: **"코드를 마지막에 쓴다."**

### 9장 · 비교 A — 비용

막대 3개 × 3지표(시간 / 왕복 / 오류). 라벨 필수.
여기에 **첫 PASS 시점 곡선**을 넣을 수 있으면 가장 강력하다 (A vs B에서 쓴 형식).

```
채점 Total
  55 |                    ③●────────────
  53 |                 ③● PASS
  40 |        ②●
  30 | ②●        ①/②(코드만)
   0 |
     +----+----+----+----+----+--> 사용자 왕복 수
       1    5   12   30   57
```

이 곡선의 메시지: **기본 AI는 시작점이 높지만 거기서 오래 머문다. 저장소는 PASS선을 빨리 넘는다.**

### 10장 · 비교 B — 품질 (의도적으로 김 빼기)

| | ② 기본 AI | ③ 저장소 AI |
|---|---|---|
| 최종 채점 | `측정 예정` | `측정 예정` |
| 참고 — 운영 모니터 선행 비교 | 60 / 62 PASS | 61 / 62 PASS (Δ=1) |

슬라이드 한 줄: **"왕복을 충분히 하면 최종 품질은 수렴한다. 저장소의 값은 품질이 아니라
거기까지 가는 비용과, 수렴하지 않는 한 가지다."** → 바로 11장으로 넘긴다.

(선행 비교가 다른 과제라는 점을 각주로 반드시 밝힌다.)

### 11장 · 비교 C — 숨은 결함 ★ 클라이맥스

세 단계로 쌓는다.

1. **"코드가 있다 ≠ 동작한다"** — Hard Gate. 소스만 있고 활성화·실기 증거가 없으면 채점 상한 44/62.
   선행 비교에서 1턴 산출물은 완성처럼 보였지만 실제 30/62 FAIL이었다.
2. **덤프는 오히려 안전하다** — 틀린 필드로 SELECT하면 덤프가 나고, 덤프는 즉시 발견된다.
3. **진짜 위험은 조용히 틀린 수량** — `MARD` 위탁 필드와 `MKOL` 이중 계상은 덤프가 나지 않는다.
   숫자만 틀린다. 트리 소계는 더 심하다: 표시 상한으로 행을 자르면 상위 노드 소계가
   **일부 합계**가 되고, 사용자는 그 소계를 보고 판단한다 (PROC-007 → 자르지 않고 막는 설계).

마무리 한 줄: **"재고 수량이 틀린 리포트는, 리포트가 없는 것보다 나쁘다."**

### 12장 · 차이를 만든 장치

장치는 3개뿐이라고 단순화한다.

| 장치 | 무엇을 막는가 | 실제로 작동한 증거 |
|---|---|---|
| **게이트** — 코드 전에 화면 이미지·필드맵 합의 | 코드 완성 후 요구사항 재작업 | 계층 4단 → 5단 개정이 **코드 생성 전**에 발생. 코드 재작업 0회 |
| **패턴 대장** — `practice/error-patterns.md` 전수 대조 후 코드 생성 | 같은 오류 재발 | 1차 세션의 ERR-005·006이 2차 세션 코드에 선반영돼 **재발하지 않음** |
| **실측 강제** — `확인필요` 3건 초과 시 코드 생성 중단, 점검 리포트 선행 | 추측이 코드에 들어가는 것 | 점검 리포트 1회 실행으로 `확인필요` **3건 → 0건** |

한 줄: **"세션 폴더는 격리하고 지식은 `practice/`로만 넘긴다 — 이 설계가 실제로 작동했다."**

### 13장 · 한계 (정직 고지)

| 한계 | 내용 |
|---|---|
| ① 65h는 추정 | 생산성 40~60 LOC/h는 업계 통용 범위를 보수적으로 잡은 값이며 **사내 실적 데이터가 아니다** |
| 순작업 기준 | 대기·협의·승인·TR 이송 시간 미포함. 실제 조직에서는 이 외부 요인이 더 클 수 있다 |
| 선행 투자 제외 | 하네스 구축 비용(공통 자산 2,214행, 커밋 25건)이 ③ 수치에서 빠져 있다 |
| 과제 1건 | 조회성 리포트 1건의 결과다. 저장·전송이 들어가는 프로그램으로 일반화할 증거가 아니다 |
| 미검증 잔여 | 권한 오브젝트 1건과 화면 전환 후 트리 실제 표시는 실행 확인을 받지 않았다 (`verify.md` §4) |
| 사람 역할 대체 불가 | SAP 접속·활성화·실행·화면 작성은 전부 사람 몫이었다 |

## 6. ② 조건 측정 프로토콜 (발표 전 선행 작업)

공정한 비교가 되려면 ② 를 **같은 과제·같은 채점표**로 1회 재현해야 한다.
저장소에 선례가 있다 — `docs/guides/replay-quality-test.md` 의 Mode H / Mode A.

### 6.1 실행

| 단계 | 내용 |
|---|---|
| 1 | **새 채팅**을 연다. 저장소를 열지 않은 상태(또는 `SKILL.md`·`HARNESS.md`·`practice/`·`sessions/` 가 없는 작업 공간) |
| 2 | 첫 메시지로 `00-intake.filled.md` §2~§7 의 **요구사항 본문만** 붙여넣는다. 게이트·패턴·복붙 계약 언급 금지 |
| 3 | 이후 사람 메시지 수를 센다. AI가 되물은 횟수는 별도 열(`Q_agent_ask`) |
| 4 | 산출된 소스를 SE38에 붙여넣고 활성화·실행한다. 오류 첨부 횟수를 `E_compile`·`E_runtime`로 센다 |
| 5 | **중단 기준을 미리 정한다** — 예: `Q_user = 20` 도달 또는 채점 PASS 도달 시 종료. 정하지 않으면 비교가 아니라 체력전이 된다 |
| 6 | 같은 채점표로 ②·③ 를 채점한다. 채점자는 사람이고, AI 자가선언은 점수화하지 않는다 |

### 6.2 채점표

운영 모니터용 62점 채점표는 그대로 못 쓴다. **재고 트리용으로 항목을 바꿔 1회 작성**해야 한다.
구조(S1 기능 / S2 비기능·기동 / S3 UX / S4 전달, 항목별 0·1·2, 증거코드, Hard Gate)는 유지하고
항목만 교체한다. 재고 트리 과제의 채점 항목 후보:

| 섹션 | 항목 후보 |
|---|---|
| S1 기능 | 5단 트리 전개 / 노드 소계(단위 혼재 A안) / 재고 유형 3구분 / 특별재고 7종 / 평가액 옵션 / 재고 0 숨기기 / 자재 더블클릭 MM03 / 입력 6조건 / 전건 조회 차단 / 표시 상한 |
| S2 비기능·기동 | 읽기 전용 / `SELECT *` 없음 / 루프 내 SELECT 없음 / `FOR ALL ENTRIES` 빈 체크 / `SY-SUBRC` 전수 / 권한 체크 지점 / **SE38 활성화** / **화면 기동** / **조회 실실행** / **더블클릭 실동작** |
| S3 UX | 계층 머리글·노드 레이아웃 / 수량 열 정렬·단위 / 0건 모달 / 상한 초과 안내 / 주석 한국어+영문 |
| S4 전달 | 단일 붙여넣기 소스 / **SE51 화면 정의서(요소 목록 탭 단위)** / **SE41 상태·타이틀** / **선택 텍스트 전수표** |

> S4의 3개 항목이 ②·③ 를 가장 크게 가를 지점이다. 코드로 복붙할 수 없는 GUI 수작업 산출물이고,
> ③ 에서도 이것 때문에 재요청 4왕복이 났다 (PROC-005·006으로 닫음).

### 6.3 공정성 규칙 (발표에서 밝힐 것)

| 규칙 | 이유 |
|---|---|
| 같은 요구사항 원문을 쓴다 | ② 에 더 빈약한 요구사항을 주면 비교가 조작된다 |
| 같은 채점표·같은 채점자 | §2 원칙 |
| ② 의 중단 기준을 미리 공개 | "충분히 안 해 봤다"는 반박을 막는다 |
| ③ 의 선행 투자 비용을 명시 | ③ 은 패턴 대장 19건을 이미 갖고 시작한다. 이 비대칭을 숨기면 안 된다 |
| ② 에서 AI가 잘한 것도 보고한다 | 한쪽만 깎으면 발표 전체의 신뢰가 깎인다 |

## 7. 예상 질문과 답

| 질문 | 답 |
|---|---|
| "65시간은 어떻게 나온 숫자인가?" | 9개 작업으로 분해해 추정했고 산정 내역을 6장에 그대로 공개한다. 코딩 구간은 통상 생산성 40~60 LOC/h를 보수적으로 적용했다. **사내 실적 데이터로 교체하면 정확도가 올라간다** — 그래서 14장에서 데이터를 요청한다 |
| "그냥 AI에게 몇 번 더 물어보면 되는 거 아닌가?" | 맞다. 그래서 10장에서 **최종 품질은 수렴한다**고 먼저 밝혔다. 차이는 거기까지 가는 왕복 수와, 수렴하지 않는 한 가지(숨은 결함)다 |
| "저장소 없이도 프롬프트를 잘 쓰면 되지 않나?" | 상당 부분 그렇다. 저장소가 하는 일은 **그 좋은 프롬프트를 매번 기억하는 것**이다. 패턴 대장이 그 기록이고, 1차 세션 오류가 2차 세션에 선반영돼 재발하지 않은 것이 증거다 |
| "AI가 틀린 코드를 주면?" | 이번에도 활성화 오류 3건·실행 오류 2건이 났고 모두 사람이 SAP에서 발견했다. **AI 산출물은 검증 전 초안이다.** 다만 1건당 5~20분에 해소됐다 |
| "AI가 SAP에 직접 접속하나?" | 접속하지 않고 접속 정보를 요구하지도 않는다. 붙여넣기·활성화·실행은 전부 사람이 했다 |
| "재고 숫자가 틀릴 위험은?" | 가장 큰 위험이었고 11장의 주제다. 이중 계상 지점을 점검 리포트로 사전에 제거했다. 다만 **권한 설정 1건과 평가액 계산 방식은 아직 실제 검증 대기 중**이다 |
| "선행 투자는 얼마 들었나?" | 공통 자산 2,214행 / 커밋 25건 / 세션 2건의 학습이다. 13장에서 ③ 수치에 포함되지 않았음을 밝히고, 14장에서 3번째 프로그램부터 손익분기라고 말한다 |
| "다른 프로그램 유형에도 되는가?" | 조회성 리포트는 바로 적용 가능하다. 저장·전송이 들어가면 검증 절차를 늘려야 한다. 13장의 한계로 명시한다 |
| "왕복 43턴은 많은 것 아닌가?" | 43턴 중 설계를 전진시킨 턴이 31턴(72%)이다. 되돌아간 12턴 중 4턴은 AI가 화면·텍스트 정의를 빠뜨려 생긴 것이고, 패턴 등록으로 그 경로를 닫았다 |
