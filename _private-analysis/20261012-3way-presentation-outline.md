## 1. 비교 설계 — 품질을 고정하고 비용을 잰다

### 1.1 세 조건

| 조건 | 정의 |
|---|---|
| **① AI 미활용** | ABAP 경력 3~5년 개발자 1명이 수작업으로 제작 |
| **② 기본 AI** | 저장소(SKILL·HARNESS·practice) 없이 일반 AI 채팅에 요구사항만 주고 제작 |
| **③ 저장소 기반 AI** | 현 저장소 하네스 적용. 인터뷰 → Gate U/D/F → Gate 2 → Gate 3 → Verify |

### 1.2 품질은 통제변수다 (이 발표의 전제)

세 조건 모두 **같은 완료 기준(DoD)에 도달한 상태**를 비교한다. "③ 이 더 좋은 코드를 만든다"는
주장은 하지 않는다. 선행 비교(`parity-score-A-vs-B-2026-08.md`, 운영 모니터 과제)에서
왕복을 충분히 하면 최종 품질이 수렴한다는 것이 이미 확인됐다 — **A=60 / B=61 (만점 62, Δ=1,
둘 다 PASS)**. 품질로 싸우면 "몇 번 더 물어보면 되지 않나"로 반박되고 그 반박이 맞다.

**그래서 측정 대상은 "같은 품질선에 도달하기까지 지불한 비용"이다.**

완료 기준 (세 조건 공통, 하나라도 미달이면 미완료로 센다)

| # | 완료 조건 |
|---|---|
| 1 | SE38 활성화 성공 (구문·타입 오류 0건) |
| 2 | 화면 기동 + 5단 트리 실제 표시 |
| 3 | 특별재고 7종(E·Q·V·W·K·M·O) 수량이 이중 계상 없이 집계 |
| 4 | 노드 소계·평가액 표시, 자재 더블클릭 → `MM03` 동작 |
| 5 | 전건 조회 차단·0건 분기·표시 상한 동작 |
| 6 | SE51 화면 / SE41 상태·타이틀 / 선택 텍스트 **입력값이 표로 제공됨** |

### 1.3 비용 4지표

| 지표 | 정의 | 왜 이걸 재는가 |
|---|---|---|
| **Q_user** | 사람이 AI에게 보낸 메시지 수 | 사용자가 실제로 쓴 왕복 |
| **E_compile** | 활성화·구문 오류를 AI에게 첨부한 횟수 | 되돌아간 횟수 |
| **E_runtime** | 덤프·빈 화면 등 실행 증상 첨부 횟수 | 되돌아간 횟수 |
| **SAP 왕복** | 사용자가 SAP GUI에서 직접 작업해 결과를 회신한 횟수 | **위임 불가 노동.** AI는 SAP에 접속하지 않으므로 이 횟수가 사용자 부담의 실체 |
| **소요 시간** | 1건 완료까지 man-hour | 최종 환산 지표 |

> `SAP 왕복`을 지표에 넣은 것이 이 발표의 차별점이다. 질문 횟수는 "채팅 좀 더 하면 되지"로
> 가볍게 들리지만, SAP 왕복은 붙여넣기·구문검사·활성화·실행·결과 회신이 전부 **사람 손**이라
> 청중(특히 개발자)이 비용으로 체감한다.

## 2. 3조건 비용 수치 (발표 1장에 그대로 쓸 종합표)

| 비용 지표 | ① AI 미활용 | ② 기본 AI | ③ 저장소 AI |
|---|---|---|---|
| **수행 시간** | **65 h** `추정` | **20 h** `추정` | **4.6 h** `실측` |
| 시간 범위 | 40 ~ 100 h | 14 ~ 28 h | 실측 단일값 |
| **AI 질문·왕복** (`Q_user`) | 해당 없음 | **약 50 턴** `추정` | **43 턴** `실측` |
| ├ 설계 전진 왕복 | — | 약 10 턴 (20%) `추정` | 31 턴 (72%) `실측` |
| └ 재작업·오류 회수 왕복 | — | **약 40 턴 (80%)** `추정` | 12 턴 (28%) `실측` |
| **활성화·구문 오류** (`E_compile`) | 조사 공수로 흡수 | **약 20 건** `추정` | **3 건** `실측` |
| **실행 오류** (`E_runtime`) | 조사 공수로 흡수 | **약 7 건** `추정` | **2 건** `실측` |
| **SAP 왕복** (사용자 직접 작업) | 전 과정 | **약 28 회** `추정` | **6 회** `실측` |
| 코드 생성 후 요구사항 재작업 | 해당 없음 | 약 8 왕복 `추정` | **0 회** `실측` |
| 완료 기준 도달 | 도달 | 도달 | 도달 |

### 2.1 배수

| 비교 | 시간 | 해석 |
|---|---|---|
| ① → ② | 65 h → 20 h | **3.3 배 단축** — AI를 쓰기만 해도 얻는 몫 |
| ② → ③ | 20 h → 4.6 h | **4.3 배 단축** — **저장소가 추가로 만든 몫** |
| ① → ③ | 65 h → 4.6 h | **14.1 배 단축** |

> 발표에서 쓸 한 줄: **"AI를 쓰면 3배, 저장소까지 쓰면 14배다. 그 사이의 4.3배가 이 발표의 주제다."**

### 2.2 ② 수치의 성격 (반드시 슬라이드에 표기)

②는 **아직 재고 트리 과제로 측정되지 않았고, 위 수치는 추정값이다.** 산정 근거는 부록 A에
구간별로 분해해 두었다. 추정 방식은 ① 의 65 h 와 동일하다 — 작업을 구간으로 쪼개고 구간별로
③ 의 실측값과 비교해 배수를 적용했다.

| 항목 | 내용 |
|---|---|
| 근거 유형 | ③ 실측 구간값 + 선행 A/B 비교 실측 비율(`Q_user 63→16`, `E_compile 18+→2`) |
| 표기 방법 | 모든 ② 칸에 `추정` 라벨. 표 하단에 "②는 추정, ③은 실측" 1줄 고정 |
| 업그레이드 경로 | §7 프로토콜로 1회 재현 측정하면 추정값을 실측값으로 교체 가능 |
| 발표에서의 태도 | 먼저 추정임을 밝힌다. 숨기고 지적받으면 발표 전체의 신뢰가 깎인다 |

### 이 배치를 고른 이유

- **3장(측정 규칙)에서 품질을 한 번에 끝낸다.** 비용축 발표의 최대 리스크는 "싸게 만든 건
  품질이 낮은 거 아닌가"다. 완료 기준 6항을 제시하고 "세 조건 모두 이걸 통과한 상태를
  비교한다"고 못 박으면 이후 모든 비용 수치가 공정해진다. 품질을 뒤에서 다시 꺼내면
  축이 흔들린다.
- **10장과 11장이 이 발표의 본체다.** 9장(종합표)은 숫자를 보여 주지만 **왜** 그 차이가
  생겼는지는 설명하지 않는다. 10장이 차이의 모양(곡선)을, 11장이 차이의 원인(지불 방식)을
  보여 준다. 시간이 부족하면 9장을 줄이고 10·11장을 지킨다.
- **6→7→8 순서는 청중의 기대를 따라간 것이다.** ①에서 65시간에 놀라고 → ②에서 "AI 쓰면
  되네"로 안심하고 → ③에서 "②는 아직 19시간 남아 있었다"로 뒤집는다. 세 장은 **같은 레이아웃**
  (구간별 시간 / 왕복 / 오류 / SAP 왕복)으로 고정해 숫자만 다르게 한다.
- **12장(장치)을 비교 뒤에 둔 이유.** 장치를 먼저 설명하면 "방법론 소개 발표"가 된다.
  결과를 먼저 보여 주고 원인을 설명하는 순서가 설득력이 높다.

하단 2줄 고정

> 세 조건 모두 **같은 완료 기준**에 도달한 상태다. 품질이 아니라 **거기까지의 비용**을 비교했다.

### 3장 · 측정 규칙

왼쪽에 **고정한 것**, 오른쪽에 **측정한 것**을 둔다.

| 고정 — 완료 기준 6항 (품질) | 측정 — 비용 4지표 |
|---|---|
| ① SE38 활성화 성공 | `Q_user` AI에게 보낸 메시지 수 |
| ② 화면 기동 + 5단 트리 실제 표시 | `E_compile` 활성화·구문 오류 첨부 횟수 |
| ③ 특별재고 7종 이중 계상 없이 집계 | `E_runtime` 덤프·빈 화면 첨부 횟수 |
| ④ 소계·평가액·MM03 더블클릭 동작 | `SAP 왕복` 사용자가 SAP에서 직접 작업한 횟수 |
| ⑤ 전건 조회 차단·0건 분기·표시 상한 | `소요 시간` 1건 완료까지 man-hour |
| ⑥ SE51·SE41·선택 텍스트 입력값 표 제공 | |

강조 한 줄: **"질문 수는 비용이지 품질 점수가 아니다. 그래서 두 축을 섞지 않는다."**

보조 한 줄: "소스가 있다고 완료가 아니다. 위 6항을 통과해야 완료로 센다."

### 5장 · 비용은 어디서 발생하는가

이 장이 11장의 밑밥이다. **코딩이 아니라 "모르는 것"에서 비용이 난다**는 것을 4개 실측 사실로
보여 준다. 이 4건은 세션에서 **추측으로는 맞힐 수 없었던 것**이다.

| 알아내야 했던 것 | 실측 결과 | 추측했다면 |
|---|---|---|
| `MSKU` (고객 특별재고) | **보류 필드 없음** | 없는 필드로 SELECT → `DBIF_RSQL_INVALID_RSQL` 덤프 |
| `MSLB` (공급업체 보유) | **보류 필드 없음 + `LGORT` 키 없음** | 저장위치 조건 입력 시 결과 왜곡 |
| `MARD` 위탁 필드 | `KLABS`·`KINSM`·`KEINM`·`KSPEM` 존재 | `MKOL`과 **이중 계상** → 수량이 두 번 더해짐 |
| `MBEW` 평가 | `LBKUM`·`SALK3`, `BWTAR = space` | 평가액 계산식 오류 → 금액 전체 오차 |

덧붙일 난이도 요인 3가지

- 재고 테이블이 **7개로 갈라진다** (`MARD`·`MSKA`·`MSPR`·`MSKU`·`MKOL`·`MSLB` + `MBEW`)
- 특별재고 참조 키가 테이블마다 다르다 (`VBELN+POSNR` / `PSPNR` / `KUNNR` / `LIFNR`)
- `CL_GUI_ALV_TREE` 는 **클래스 내부에서도 작명 관례가 갈린다** (생성자는 접두어 없음, 메서드는 `i_`·`is_`·`it_`)

한 줄: **"이 과제의 비용은 타이핑이 아니라 조회에서 나온다. 그래서 세 조건이 갈린다."**

### 10장 · 비용 곡선 ★

**이 발표에서 가장 강력한 한 장이다.** x축을 누적 소요 시간, y축을 완료 기준 도달률로 둔다.

```
완료 도달률
 100% |  ③●         ②●                                    ①●
      |   ╱        ╱
  90% |  │    ╭───●  ← ② 는 여기서 10시간을 더 쓴다
      |  │   ╱
  80% |  │  ●
      | ╱  ╱
  60% |●  ●  ← ② 1차 코드 (30분)
      |
   0% +──┴──┴────┴────────┴──────────────────────┴────
        0.5 1   4.6      10          20          65   (h)
```

| 조건 | 곡선의 모양 |
|---|---|
| ① | 거의 선형. 조사·설계·코딩·테스트를 순서대로 지불한다 |
| ② | **초반 급상승 후 장기 정체.** 30분에 60%, 4시간에 80%, 10시간에 90% — 그리고 마지막 10%에 10시간 |
| ③ | 초반이 느리다 (인터뷰·게이트에 1.7시간). 그 대신 **90% 이후 구간이 짧다** |

핵심 메시지 2줄

> **②의 곡선은 빨리 올라가다 길게 눕는다.** "거의 다 된 것 같은데 끝나지 않는 구간"이 비용의 본체다.
> **③은 앞에서 천천히 간다.** 인터뷰와 게이트에 쓴 1.7시간이 뒤의 긴 꼬리를 잘라낸다.

> 발표 노트: ②의 "90% 함정"은 청중 대부분이 직접 겪어 본 경험이다. 이 곡선에서 고개를
> 끄덕이게 만들면 11장이 쉽게 들어간다. 반대로 이 장을 건너뛰면 11장이 기술 설명으로 들린다.

### 11장 · 같은 작업, 다른 지불 방식 ★

**비용 차이의 원인을 설명하는 장이다.** 세 조건이 하는 **일은 같다** — 다섯 가지를 알아내야 한다.
다른 것은 **그 비용을 어떻게 지불하는가**다.

| 알아내야 할 것 | ① 지불 방식 | ② 지불 방식 | ③ 지불 방식 |
|---|---|---|---|
| 재고 7테이블 필드 구성 | SE11·SE16N 조사 **6 h** | 추측 → 덤프·구문오류 **12왕복 / 6.0 h** | 점검 리포트 1회 실행 **20 분** |
| `CL_GUI_ALV_TREE` API 시그니처 | 표준 데모 분석 **8 h** (구현 포함) | 구문 오류 **6왕복 / 1.5 h** | 패턴 선반영 + **3왕복 / 18 분** |
| 컨트롤을 띄우는 올바른 구조 | 경험·검색 (위 8 h 포함) | 렌더링 실패 **5왕복 / 2.5 h** | 1차 세션 교훈 적용 **20 분** |
| 화면·상태·선택 텍스트 입력값 | 직접 작성 **3 h** | **7왕복 / 2.5 h** | 기준 문서 기반 제공 **46 분** |
| 요구사항 세부 (계층 5단·소계 규칙) | 현업 미팅 2회 **6 h** | **코드 생성 후** 재작업 **8왕복 / 2.5 h** | **코드 생성 전** 게이트 합의, 재작업 **0 회** |

세 가지 결론을 이 표에서 읽어 준다.

1. **②는 "추측하고 틀리면서 배우는" 방식으로 지불한다.** 컴파일러와 덤프가 선생님이고,
   한 번에 한 건만 알려 준다. 그래서 왕복이 선형으로 쌓인다.
2. **③은 "한 번에 물어보고 기록해 두는" 방식으로 지불한다.** 점검 리포트 1회로 7테이블
   24필드를 확정했고(`확인필요` 3건 → **0건**), 그 결과를 패턴 대장에 남겨 다음 세션으로 넘긴다.
3. **①은 조사 비용을 선불한다.** 그래서 오류 회수는 적지만 총액이 가장 크다.

마지막 줄 — **비용으로 환산되지 않는 잔존 리스크**를 한 줄 덧붙인다.

> ②는 20시간을 써도 **추측이 코드에 남아 있을 수 있다.** 틀린 필드로 SELECT하면 덤프가 나서
> 즉시 발견되지만, `MARD`/`MKOL` 이중 계상은 **덤프가 나지 않고 수량만 조용히 틀린다.**
> 트리 소계는 더 위험하다 — 표시 상한으로 행을 자르면 상위 노드 소계가 **일부 합계**가 되고,
> 사용자는 그 소계를 보고 판단한다. **틀린 재고 리포트는 리포트가 없는 것보다 나쁘다.**

| 4 | 소스를 SE38에 붙여넣고 활성화·실행. 오류 첨부 횟수를 `E_compile`·`E_runtime`, SAP 조작 횟수를 `SAP 왕복`으로 센다 |
| 5 | **중단 기준을 미리 정한다** — 예: `Q_user = 60` 도달 또는 완료 기준 6항 통과 시 종료. 정하지 않으면 비교가 아니라 체력전이 된다 |
| 6 | 완료 기준 6항을 **사람이** 판정한다. AI 자가선언은 인정하지 않는다 |

### 공정성 규칙 (발표에서 밝힐 것)

| 규칙 | 이유 |

### A.3 범위와 교차 검증

| 시나리오 | 시간 | 조건 |
|---|---|---|
| 낙관 | **14 h** | 재고 테이블 구성을 AI가 상당 부분 맞힘, 렌더링 함정을 1왕복에 통과, 화면 정의를 한 번에 요구 |
| **기준** | **20 h** | 위 표의 구간 합계 |
| 비관 | **28 h** | 이중 계상을 후반 검증에서 발견해 집계 구조 재작업, 렌더링 함정에서 장기 정체 |

**교차 검증 — 선행 A/B 비교와의 정합성**

운영 모니터 과제의 실측 비율은 `Q_user 63 → 16` (약 4배), `E_compile 18+ → 2` (약 9배)였다.
본 추정의 비율은 `E_compile 20 → 3` (약 6.7배), `SAP 왕복 28 → 6` (약 4.7배)로 **같은 자릿수**에
들어온다. 다만 `Q_user` 는 50 → 43 으로 비율이 1.2배에 그친다 — 이것은 의도한 결과다.

> **③ 의 43턴은 낭비가 아니라 투자다.** 인터뷰·게이트 확인에 쓴 턴이 72%이고, ② 의 50턴은
> 80%가 재작업이다. **턴 수가 비슷해 보이는 것 자체가 발표의 논점**이므로, 9장 종합표에서
> `Q_user` 를 총계만 쓰지 말고 **"전진 / 재작업" 2줄로 쪼개서** 보여 줘야 한다.

## 부록 B. 예상 질문과 답

| 질문 | 답 |
|---|---|
| **"20시간은 어디서 나온 숫자인가?"** | 9구간으로 분해해 추정했고 근거를 부록 A 에 공개한다. 각 구간은 ③ 의 실측값과 비교해 배수를 적용했다. 재현 측정 1회로 실측값으로 교체할 수 있고 절차는 준비돼 있다 |
| **"65시간은 어디서 나온 숫자인가?"** | 9구간 분해 추정이고 6장에 산정 내역을 그대로 공개한다. 코딩 구간은 통상 생산성 40~60 LOC/h 를 보수적으로 적용했다. **사내 실적 데이터로 교체하면 정확도가 올라간다** — 그래서 14장에서 데이터를 요청한다 |
| **"싸게 만들었으면 품질이 낮은 거 아닌가?"** | 세 조건 모두 **같은 완료 기준 6항**에 도달한 상태를 비교했다(3장). 품질을 비교한 발표가 아니라 **같은 품질에 도달하는 비용**을 비교한 발표다 |
| **"그냥 AI에게 몇 번 더 물어보면 되는 거 아닌가?"** | 맞다. 그게 ② 다. 그 "몇 번 더"가 **50턴 / 오류 27건 / SAP 왕복 28회 / 20시간**이다. 이 발표는 그 비용을 숫자로 센 것이다 |
| **"③ 도 43턴인데 ② 의 50턴과 큰 차이가 없다"** | 턴 수는 비슷하다. 다른 것은 **구성**이다. ③ 은 72%가 설계를 전진시킨 턴(인터뷰·게이트 확인)이고, ② 는 80%가 재작업이다. 그리고 SAP 왕복은 **6회 대 28회**로 4.7배 차이가 난다 |
| **"저장소 없이도 프롬프트를 잘 쓰면 되지 않나?"** | 상당 부분 그렇다. 저장소가 하는 일은 **그 좋은 프롬프트를 매번 기억하는 것**이다. 1차 세션의 오류 2건이 2차 세션 코드에 선반영돼 재발하지 않은 것이 증거다 |
| **"AI가 틀린 코드를 주면?"** | ③ 에서도 활성화 오류 3건·실행 오류 2건이 났고 모두 사람이 SAP 에서 발견했다. **AI 산출물은 검증 전 초안이다.** 다만 1건당 5~20분에 해소됐다 |
| **"AI가 SAP 에 직접 접속하나?"** | 접속하지 않고 접속 정보를 요구하지도 않는다. 붙여넣기·활성화·실행은 전부 사람이 했다. 그래서 `SAP 왕복` 을 비용 지표에 넣었다 |
| **"재고 숫자가 틀릴 위험은?"** | 11장 마지막 줄이 그 얘기다. `MARD`/`MKOL` 이중 계상은 덤프가 나지 않고 수량만 틀린다. ③ 은 점검 리포트로 사전 제거했다. 다만 **권한 설정 1건과 평가액 계산 방식은 아직 실제 검증 대기 중**이다 |
| **"선행 투자는 얼마 들었나?"** | 공통 자산 2,214행 / 커밋 25건 / 세션 2건의 학습이다. 13장에서 ③ 의 4.6시간에 포함되지 않았음을 밝히고, 14장에서 3번째 프로그램부터 손익분기라고 말한다 |
| **"다른 프로그램 유형에도 되는가?"** | 조회성 리포트는 바로 적용 가능하다. 저장·전송이 들어가면 검증 절차를 늘려야 한다. 13장의 한계로 명시한다 |
