# legacy/ — 기존 프로그램 자산 보관소 (개선 과제 입력)

> 운영 중인 기존 프로그램의 **원본 로직과 화면 정보**를 보관하는 곳이다.
> 개선 과제(기존 프로그램 변경)는 신규 개발과 입력이 다르다 — 요구사항 인터뷰 전에
> **현재 무엇이 어떻게 동작하는지(AS-IS)** 가 먼저 확정되어야 한다.

## 왜 `sessions/` 가 아닌가

`sessions/README.md` 규칙상 **AI는 새 세션에서 이전 세션 폴더를 참조하지 않는다.**
기존 프로그램 자산을 세션 폴더에 넣으면, 정작 개선 작업을 수행하는 다른 세션이
그 자산을 읽을 수 없다. 그래서 `context/ddic-cache.md` 와 같은 **세션 공유 자산**으로
`legacy/` 에 분리 보관한다.

| 성격 | 위치 | 타 세션 참조 |
|---|---|---|
| 세션별 요구사항·설계·코드 | `sessions/<날짜-프로그램>/` | 금지 |
| 시스템에서 확인된 DDIC 사실 | `context/ddic-cache.md` | 허용 |
| **기존 프로그램 원본 로직·화면** | **`legacy/<프로그램>/`** | **허용** |

## 폴더 규칙

```text
legacy/
  README.md                     # 이 파일
  TEMPLATE-screen-info.md       # 화면 정보 접수 양식
  <프로그램명>/                  # 예: ZMMR0010
    README.md                   # 자산 색인 + 접수 상태
    source/                     # 원본 로직 (무수정 보존)
      <오브젝트명>.abap          # 메인 프로그램
      <INCLUDE명>.abap          # 인클루드 (있는 만큼)
    screens/
      screen-info.md            # 화면 정보 (TEMPLATE 기반)
      *.png                     # 화면 캡처 (실데이터 마스킹 필수)
```

## 절대 규칙

1. **원본 무수정 보존.** `source/` 의 파일은 받은 그대로 둔다. 줄바꿈·주석·들여쓰기도
   고치지 않는다. AS-IS 비교 기준이 되기 때문이다. 개선 코드는 세션 폴더의
   `code.abap` 으로 따로 만든다.
2. **AI가 로직을 추측해 채우지 않는다.** 누락된 인클루드·서브루틴이 있으면 비워 두고
   사용자에게 요청한다. `legacy/` 에 있는 내용은 "실제 시스템에 존재하는 것"이어야 한다.
3. **실데이터·시스템 정보 금지.** 화면 캡처에 거래 데이터·사용자 ID·호스트·클라이언트가
   보이면 마스킹한 뒤 저장한다. 코드 내 하드코딩된 운영 값도 마스킹 대상이다.
4. **자동 점검 기준에서 제외.** 기존 코드는 현행 코드 표준(`SKILL.md` §3.4)을 만족하지
   않는 것이 정상이다. `tools/abap_check.py` 의 기본 스캔은 `legacy/` 를 건너뛴다.
   대신 **폴더를 직접 지정하면 점검한다** — 개선 과제의 기준선 진단 용도다.

   ```bash
   python3 tools/abap_check.py legacy/<프로그램>/source   # 기준선 지적 목록
   ```

## 접수 절차 (수집 세션)

| 순서 | 내용 | 산출 |
|---|---|---|
| 1 | 로직 수령 — 오브젝트 단위로 1개씩 | `source/<오브젝트>.abap` |
| 2 | 로직 색인 작성 — 오브젝트 목록·호출 관계·미수령분 명시 | `README.md` |
| 3 | 화면 정보 수령 — `TEMPLATE-screen-info.md` 항목 기준 | `screens/screen-info.md` |
| 4 | 기준선 진단 (선택) — 점검기 지적 목록 기록 | `README.md` |

수집 세션은 **저장까지만** 한다. 개선 설계·코드 생성은 하지 않는다.

## 개선 세션에서 쓰는 방법 (AI용)

1. `legacy/<프로그램>/README.md` 로 자산 범위와 미수령분을 먼저 확인한다.
   미수령분이 개선 범위에 걸리면 코드를 만들지 않고 사용자에게 요청한다.
2. `source/` 를 AS-IS 사실로만 쓴다. 여기에 없는 동작은 "없다"고 단정하지 않고 질문한다.
3. `screens/screen-info.md` 의 화면 구성을 Gate D 컨펌의 **출발점**으로 쓴다.
   기존 화면을 바꾸는 개선이면 변경 전/후를 나란히 제시해 컨펌받는다.
4. 개선 결과물은 `sessions/<날짜-프로그램>/code.abap` 에 쓴다. `legacy/` 를 덮어쓰지 않는다.
