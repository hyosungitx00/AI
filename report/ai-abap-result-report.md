## 0. 요약

SAP GUI 환경의 ABAP 개발은 일반 바이브 코딩이 통하지 않습니다. AI가 SAP에 접속할 수 없어 코드를
사람이 손으로 옮겨 활성화해야 하고, 테이블·필드명을 하나라도 틀리면 활성화가 실패해 작업이
처음으로 되돌아갑니다. 이 과제는 **AI에게 자유를 주는 대신 관문을 세우는 방식**으로 이 문제를 풀었습니다.

요구사항을 인터뷰로 받아 9개 게이트를 순서대로 통과시키고, 코드를 사용자에게 내보내기 전에
자동 점검기가 17개 규칙으로 기계 검사하며, 실제로 발생한 오류는 패턴으로 승격해 다음 세션의
코드 골격과 점검 규칙에 선반영됩니다. 같은 오류를 두 번 겪지 않는 구조입니다.

| 구분 | 결과 | 근거 |

## 1. 과제 개요

### 1.1 대상 업무

SAP 운영·개발 담당자가 수행하는 **커스텀 ABAP 개발 업무**입니다. 이번 과제의 주력 범위는
현업 요청 빈도가 가장 높은 두 유형으로 한정했습니다.

| 유형 | 내용 | 트랜잭션 | 과제 범위 |
|---|---|---|---|
| 01 ALV 리포트 | 선택화면 + 조회 + ALV 출력 | SE38 | 주력 |
| 03 Function Module | 재사용 로직, 배치 호출 대상 | SE37 | 주력 |
| 02 / 04~07 | Module Pool, Enhancement, Interface, Batch, Forms | SE80 등 | 확장(템플릿 보유) |

대표 요청 형태는 "여러 화면을 돌아다니며 눈으로 맞춰 보던 정보를 한 화면에서 조회하게 해 달라"는
조회성 리포트입니다. 실전 1호 과제가 정확히 이 유형이었습니다 — 구매요청(PR)의 연결 정보
(WBS·판매오더·구매오더·입고·송장)를 한 번에 조회하는 ALV 리포트.

### 1.2 추진 배경

ABAP 개발에 생성형 AI를 그대로 적용하면 일반 개발보다 **실패 비용이 훨씬 큽니다.** 네 가지 구조적
제약 때문입니다.

- **AI가 시스템을 볼 수 없다.** 접속·실행·디버깅이 불가능하므로 코드를 사람이 SE38/SE37에 손으로
  옮겨 활성화해야 합니다. AI는 자기 코드가 돌아가는지 확인할 방법이 없습니다.
- **DDIC 환각이 치명적이다.** 테이블·필드명을 하나라도 지어내면 활성화가 실패합니다. 일반 개발에서는
  컴파일 에러 한 줄이지만, 여기서는 "복붙 → 활성화 시도 → 실패 → 담당자가 오류 전문을 받아 적어
  AI에 전달 → 수정본 재복붙"이라는 왕복 사이클이 발생합니다.
- **릴리스에 따라 문법이 다르다.** ECC 6.0, NetWeaver 7.40/7.50, S/4HANA에서 쓸 수 있는 문법이
  달라, 릴리스를 모르고 생성한 코드는 활성화되지 않습니다.
- **요구사항 오해가 늦게 드러난다.** 코드를 다 만든 뒤 "원하던 화면이 아니다"가 나오면 설계부터
  다시 합니다. 조회 리포트는 화면 구성이 곧 요구사항이기 때문입니다.

즉 문제는 "AI가 코드를 잘 쓰는가"가 아니라 **"한 번에 활성화되는 코드가 나오는가"** 였습니다.

### 1.3 과제 목표

1. 요구사항 오해를 코드 생성 **전에** 걸러낸다 (화면·필드 단계에서 확인받는다).
2. DDIC 환각을 구조적으로 차단한다 (확인된 값만 사용, 모르면 질문으로 되돌린다).
3. 코드 품질 검증을 사람 기억이 아니라 **기계**가 하게 한다.
4. 한 번 겪은 오류가 다음 세션에서 재발하지 않게 **자산으로 축적**한다.

### 2.2 기존 흐름의 구조적 문제

실전 1호 세션을 수행하며 관찰된 문제를 네 가지로 정리했습니다.

- **요구사항이 말로만 오간다.** 현업이 구두나 메일로 요청하면 담당자가 머릿속에서 화면을 그립니다.
  이 그림이 틀렸다는 사실은 코드가 나온 뒤에야 드러납니다.
- **테이블·필드 확인이 매번 처음부터다.** 같은 테이블을 쓰는 프로그램을 또 만들어도 SE11을 다시
  열어 필드를 받아 적습니다. 직전에 확인한 값이 어디에도 남아 있지 않기 때문입니다.
- **코드 품질이 담당자 기억에 의존한다.** `SELECT *` 금지, `FOR ALL ENTRIES` 앞 빈 테이블 체크,
  `SY-SUBRC` 확인 같은 규칙은 알고 있어도 바쁠 때 빠집니다. 빠진 사실은 성능 문제가 터진 뒤에 압니다.
- **같은 오류를 반복해서 겪는다.** 활성화 실패 원인과 해결책이 담당자 개인 경험으로만 남아,
  다른 사람이 같은 함정에 다시 빠집니다.

### 2.3 실패 비용 구조

ABAP 개발에서 오류가 늦게 발견될수록 비용이 급격히 커집니다. 이 과제가 게이트를 앞단에 집중시킨 이유입니다.

| 발견 시점 | 되돌아가는 범위 | 비용 |
|---|---|---|
| 요구사항 단계 | 질문 한 번 | 낮음 |
| 화면 컨펌 단계 | 화면 설계 재작성 | 낮음 |
| 스펙 단계 | 테이블·조인 재설계 | 중간 |
| 활성화 단계(Syntax) | 코드 수정 + 복붙 왕복 | 높음 |
| 운영 단계(성능·권한) | 장애 대응 + 재이송 | 매우 높음 |

## 3. 개선 방법 (To-Be)

### 3.1 활용 AI 도구

| 도구 | 용도 | 비고 |
|---|---|---|
| **Cursor AI** | 주 작업 환경. 저장소 규칙 자동 적용, 인터뷰·설계·코드 생성 | `.cursor/rules/` 3종이 자동 적용되어 별도 지침 등록 불필요 |
| Cursor Cloud Agent | 저장소 구조 최적화·도구 개발 | 본 과제의 자동화 자산 구축에 사용 |
| 범용 LLM (ChatGPT·Claude 등) | 대체 수단 | `harness/prompts/system-prompt-fragment.md`를 지침으로 등록해 동일 규칙 적용 가능 |
| Python 3 (표준 라이브러리) | 자동 점검기 구동 | 외부 패키지 설치 불필요 |

SAP 시스템 자체에는 어떤 도구도 설치하지 않았습니다. 기존 SE38/SE37 작업 방식을 그대로 두고
**그 앞단에 AI 작업 체계를 붙인 방식**이라, 시스템 영향도와 보안 검토 부담이 없습니다.

### 3.2 핵심 설계 원칙 3가지

AI에게 "잘해 달라"고 요청하는 대신, 지켜야 할 계약을 명문화했습니다 (`SKILL.md` §3).

- **DDIC 그라운딩** — 테이블·필드는 담당자가 SE11에서 확인해 준 값, 또는 과거 활성화로 실재가
  증명된 값만 사용합니다. 모르는 필드는 추측 코드 대신 `[확인필요]` 주석과 질문으로 되돌립니다.
  가정이 3건을 넘으면 코드 생성을 중단하고 요구사항 단계로 회귀합니다.
- **릴리스 게이트** — 기준을 `SAP_BASIS 750 / S/4HANA`로 고정하고 코드 상단에 명시합니다.
  보수적 문법이 필요한 건에만 ECC 호환으로 내려갑니다.
- **복붙 계약** — 생성 코드는 생략 없는 완전 소스 1개, 번호 매긴 복사 순서(트랜잭션 명시),
  DDIC·메시지·T-code 정의서, T1~T3 테스트 표, 오류 회수 양식을 반드시 동반합니다.
  담당자가 추가 판단 없이 SE38에 그대로 옮길 수 있는 상태로만 전달합니다.

### 3.3 진행 절차 — 9개 게이트

각 관문은 승인 없이 다음 산출물을 만들지 않습니다. 특히 **스펙 승인 전에는 "바로 코드 줘"
요청이 와도 코드를 만들지 않습니다.**

```text
[0] 사전준비 1회 — 릴리스·패키지·네이밍 확정
      │ Gate 0
[0.5] 인터뷰 — 설계 25문항 (한 턴 최대 3문항, [모름] 허용)
      │ Gate U   AI가 이해한 내용을 확인서로 제시 → 승인
      │ Gate D   화면 텍스트 목업 컨펌
      │ Gate D-2 화면 이미지 재검증 (선택화면 S1 / 결과 S2 분리)
      │ Gate F   필드 연결표·조인·구현 방식 승인
[1] Context 수집 — DDIC 캐시 확인 → 부족분만 SE11 수집
      │ Gate 1   필수 항목 1칸이라도 비면 코드 금지
[2] 스펙 확정 — 테이블·조인·화면·예외 미니 스펙
      │ Gate 2   담당자 "OK" 전 코드 금지
[3] 코드 생성 — 골격 복제 → 세션 값 교체
      │ Gate 3   자동 점검 오류 0건 + 사람 판단 체크리스트
[4] 검증 — 활성화 → 실행 테스트 → (오류 시 회수·수정)
      │ Gate 4   "활성화 OK + T1~T3 결과" 회수 전 이관 금지
[5] 운영 이관 — T-code·권한·이송 요청서
      │ 패턴 승격 + DDIC 캐시 승격
```

전 구간이 **AI가 묻고 담당자가 답하는 형식**입니다. 담당자가 양식을 작성하거나 문서를 쓰지 않아도
되고, 모르는 항목은 `[모름]`으로 넘기면 AI가 제안으로 메우고 `[추정]`으로 표시해 다시 확인받습니다.
설계 25문항에 더해 활성화·테스트·이관 단계의 12문항까지 총 37문항이 스크립트로 정의되어 있습니다.

### 3.4 자동화 — Gate 3 자동 점검기

가장 큰 변화입니다. 사람이 체크리스트를 눈으로 대조하던 작업을 스크립트가 대신합니다.

```text
$ python3 tools/abap_check.py sessions/20261006-ZSD_DEMO_ALV01/code.abap
[점검] sessions/20261006-ZSD_DEMO_ALV01/code.abap
  ERROR   L47    CHK-005  사전 필드 `VBAK-...`를 참조하는데 `TABLES vbak.` 선언이 없습니다.
                 근거 ERR-006 · 처방: 코드 상단에 `TABLES <테이블>.` 선언을 추가하십시오.
  ERROR   L92    CHK-004  SELECT 직후 `SY-SUBRC` 체크가 없습니다.
                 근거 SKILL §3.4 · 처방: 직후에 `IF sy-subrc <> 0.` 분기(메시지 + RETURN)를 넣으십시오.
요약: 파일 1개 · 오류 2건 · 경고 0건
Gate 3 미통과 — 오류 0건이 될 때까지 코드를 사용자에게 제시하지 마십시오.
```

- 17개 규칙(`CHK-001`~`CHK-017`)으로 `SELECT *`, 루프 내 SELECT, `FOR ALL ENTRIES` 빈 체크,
  `SY-SUBRC`, `TABLES` 선언, 릴리스 문법, 헤더·부록, 주석 병기 등을 점검합니다.
- 모든 지적에 **근거(패턴 ID·규칙 조항)와 처방 한 줄**이 붙습니다. 결과를 그대로 AI에 돌려주면
  수정이 되므로, 담당자가 ABAP 문법을 판단하지 않아도 품질이 수렴합니다.
- 소요 시간은 저장소 전체 기준 **0.04초**(3회 실측 평균)입니다. 사람이 8항목을 대조하던 작업을
  사실상 무비용으로 대체합니다.
- 기계가 판별할 수 없는 항목(존재하지 않는 필드, 조인의 업무 타당성, 화면 구조 오인)은
  **"사람 판단"으로 명시 분리**했습니다. 자동화가 사람 검토를 밀어내지 않도록 한 설계입니다.
- 외부 패키지 없이 Python 3만으로 동작하고, 자체 테스트 32항목이 규칙의 정상 동작을 보증합니다.

### 3.5 학습 구조 — 오류가 자산이 되는 경로

이 과제의 핵심 차별점입니다. 한 번 겪은 오류는 네 단계로 승격되어 재발이 차단됩니다.

```text
① 활성화 실패 발생
      ↓ 담당자가 오류 전문 회수 (양식 고정)
② practice/error-patterns.md 에 패턴 승격 (ERR / MSG / PROC)
      ↓ 기계 판별이 가능하면
③ tools/abap_check.py 에 CHK 규칙 추가 → 코드 제시 전 자동 차단
      ↓ 모든 신규 프로그램에 해당하면
④ templates/abap/ 코드 골격에 선반영 → 애초에 그렇게 생성됨
```

실제 사례 — 실전 1호 세션에서 `SELECT-OPTIONS ... FOR eban-badat` 사용 시 `TABLES eban.` 선언이
없어 활성화에 실패했습니다. 이 오류는 `ERR-006` 패턴으로 등록되고, `CHK-005` 점검 규칙이 되고,
코드 골격 3종에 선반영되었습니다. 현재 동일 오류는 담당자에게 전달되기 전에 기계가 차단합니다.

### 3.6 저장소 구성

규칙·입력·산출·검증 네 층으로 구성했습니다. 하네스 자산 기준 62개 파일, 약 4,130줄입니다
(본 리포트 산출물 `report/` 제외).

| 층 | 경로 | 역할 |
|---|---|---|
| 규칙 | `SKILL.md`, `HARNESS.md`, `AGENTS.md`, `.cursor/rules/` | AI 행동 규칙, 절차, Cursor 자동 적용 규칙 3종 |
| 입력 | `requirements/`, `context/`, `harness/prompts/` | 요구사항 템플릿 13종, 시스템·DDIC 정보, 인터뷰 스크립트 |
| 산출 | `templates/abap/`, `examples/`, `sessions/` | 코드 골격 3종, 출력 기준 샘플 2종, 세션별 기록 |
| 검증 | `tools/`, `harness/checklists/`, `practice/`, `.github/workflows/` | 자동 점검기·테스트, 체크리스트, 오류 패턴 10건, CI |

Cursor로 저장소를 열면 규칙이 자동 적용되므로, 담당자는 **지침을 붙여넣지 않고 바로 요청**하면 됩니다.
ABAP 파일을 편집하면 코드 표준 규칙이 자동으로 함께 적용됩니다.

### 4.1 검증된 정량 효과 (저장소 재현 가능)

아래는 추정이 아니라 저장소에서 명령으로 재현되는 실측값입니다 (재현 명령은 부록 D).

| 지표 | As-Is | To-Be | 효과 |
|---|---|---|---|
| 코드 품질 점검 방식 | 수동 체크리스트 8항목 대조 | 명령 1회 자동 점검 17규칙 | 점검 항목 2.1배, 소요 **0.04초** |
| 점검 누락 가능성 | 담당자 기억·집중도 의존 | 종료코드로 강제(오류 시 비통과) | 누락 구조적 차단 |
| 잠복 결함 발견 | — | 기준 샘플에서 1건 발견·수정 | 도입 즉시 실결함 검출 |
| 현재 ABAP 산출물 품질 | — | 6개 파일 오류 0건 | CI로 상시 유지 |
| 재발 방지 자산 | 담당자 개인 경험 | 패턴 10건 + 규칙 17건 + 골격 3종 | 조직 자산화 |
| 코드 작성 출발점 | 빈 화면 | 골격 3종(패턴 선반영) | 기본 품질 보장 상태에서 시작 |
| 요구사항 확인 시점 | 코드 완성 후 | 화면·필드 단계(Gate D/F) | 재작업 범위 축소 |

특히 **"기준 샘플에서 1건 발견"** 은 자동화의 가치를 그대로 보여 준 사례입니다. 출력 형식의 기준으로
쓰이던 예제 코드 자체에 `TABLES` 선언 누락(ERR-006)이 잠복해 있었고, 사람은 수개월간 알지 못했으나
점검기 도입 즉시 검출되었습니다. 기준 샘플의 결함은 그것을 참고한 모든 후속 코드로 전파되므로,
발견 시점이 이를수록 회피 비용이 큽니다.

### 4.2 실전 적용 사례 — ZMM_PR_LINK_ALV01

데모가 아니라 **실제 SAP 시스템에 활성화되어 테스트까지 완료된 건**입니다.

| 항목 | 내용 |
|---|---|
| 프로그램 | `ZMM_PR_LINK_ALV01` (SE38 실행 리포트, 패키지 `ZMM01`) |
| 업무 | 구매요청(PR) 연결 정보 일괄 조회 — WBS·판매오더·구매오더·입고·송장 |
| 요구사항 접수 | 인터뷰 방식. 담당자가 테이블을 몰라 `[모름]`으로 답 → AI 제안 후 확인 절차로 전환 |
| 화면 확정 | 텍스트 목업 컨펌 → 이미지 1차 반려(합성형) → S1/S2 분리형 재제출 후 컨펌 |
| 선택화면 | PR번호(선택), 생성일(범위·기본 당일), 플랜트·구매그룹(선택) |
| 입력 검증 | 전체 미입력 차단, 생성일 90일 상한, 일자 역전 차단 |
| 출력 | ALV 8열 + `CL_SALV_TABLE` + 엑셀 + 문서번호 드릴다운 |
| 활성화 | Syntax 오류 1건(`ERR-006`) → 수정 후 **0건** |
| 실행 테스트 | T1 정상 ALV / T2 규정 메시지 / T3 규정 메시지 — **전부 통과** |
| 운영 이관 | 권한 목록(`M_BANF_WRK`), TR 초안, 배치잡 불필요 판정까지 완료 |
| 승격 자산 | `ERR-006`, `MSG-002`, `PROC-001` 3건을 공용 패턴으로 등록 |

이 1건에서 얻은 것은 프로그램 하나가 아닙니다. **다음 세션부터 적용되는 재발 방지 자산 3건**과,
인터뷰 방식이 "담당자가 테이블을 몰라도 설계가 진행된다"는 사실의 검증입니다.

### 4.3 시간·비용 절감 측정

업무 공수 절감은 사내 실측값이 필요합니다. 아래 계산식과 양식에 실측값을 넣으면 산출됩니다.
상세 양식은 `report/effect-worksheet.md`(부록 B)에 있습니다.

```text
① 1건 절감 공수   = As-Is 1건 공수 − To-Be 1건 공수
② 절감률(%)       = ① ÷ As-Is 1건 공수 × 100
③ 연간 절감 공수   = ① × 연간 수행 건수
④ 연간 절감 금액   = ③ × 시간당 인건비
⑤ 재작업 회피 효과 = (As-Is 평균 활성화 재시도 횟수 − To-Be 재시도 횟수)
                     × 1회 왕복 공수 × 연간 건수
```

| 입력 항목 | 실측값 | 출처 |
|---|---|---|
| As-Is 1건 공수 | [실측 기입] | 최근 유사 건 3건 평균 |
| To-Be 1건 공수 | [실측 기입] | ZMM_PR_LINK_ALV01 소요 실적 |
| 연간 수행 건수 | [실측 기입] | 요청 접수 이력 |
| 시간당 인건비 | [실측 기입] | 사내 표준 단가 |
| As-Is 활성화 재시도 | [실측 기입] | 담당자 기록 |
| To-Be 활성화 재시도 | **1회** (실측) | 실전 1호 Syntax 오류 1건 |

> 아래는 계산 방식을 보여 주는 **예시이며 가정값입니다.** 실측값으로 반드시 교체하십시오.
> 예시: As-Is 5.0 MD, To-Be 2.0 MD, 연 12건, 단가 X원/시간 가정 시
> → 1건 절감 3.0 MD, 절감률 60%, 연간 절감 36 MD, 금액 = 36 MD × 8h × X원.

측정 시 유의할 점은 **To-Be 공수에 인터뷰 응답 시간을 포함**해야 한다는 것입니다. 이 체계는
담당자의 문서 작성 시간을 질문 응답 시간으로 바꾼 것이므로, 응답 시간을 빼면 절감이 과대 계상됩니다.

### 4.4 오류 감소

| 지표 | 값 | 비고 |
|---|---|---|
| 실전 1호 활성화 오류 | 1건 → 0건 | 1회 수정으로 해소 |
| 해당 오류의 재발 가능성 | 구조적 차단 | 패턴·점검 규칙·코드 골격 3중 선반영 |
| 기계 점검이 사전 차단하는 오류 유형 | 17종 | 패턴 연계 6종 포함 |
| 자동 점검으로 발견한 잠복 결함 | 1건 | 기준 샘플 ERR-006 |
| 점검기 자체 신뢰성 | 테스트 32항목 통과 | 규칙 오탐·미탐 회귀 방지 |
| CI 상시 검증 | 커밋·PR마다 실행 | 품질 하락 유입 차단 |

점검기 개발 과정에서 **점검기 자체의 결함 2건**(오류 줄번호 오표기, 테스트 데이터 오점검)도
자체 테스트로 발견해 수정했습니다. 검증 도구를 검증하는 구조까지 갖춘 상태입니다.

### 4.5 정성 효과

- **담당자 진입 장벽 하락** — 테이블·필드를 몰라도 `[모름]`으로 답하면 설계가 진행됩니다.
  실전 1호에서 실제로 이 경로로 완료되었습니다.
- **요구사항 확정의 증거화** — 화면 컨펌·필드 승인이 세션 폴더에 기록으로 남아, "이렇게 요청한 적
  없다"는 분쟁 여지가 줄어듭니다.
- **품질이 사람에 종속되지 않음** — 경력·집중도와 무관하게 동일 규칙이 적용됩니다.
- **인수인계 비용 감소** — 설계 의도, 테스트 결과, 권한·이송 정보가 세션 폴더에 묶여 있습니다.

## 5. 확산 가능성 및 향후 계획

### 5.1 확산 가능성

세 축으로 확산이 가능하며, 각 축에서 재사용되는 자산이 다릅니다.

| 확산 축 | 대상 | 재사용 자산 | 추가 필요 작업 |
|---|---|---|---|
| 모듈 확산 | 같은 담당 조직의 다른 SAP 모듈 (SD·MM·FI·PP) | 규칙·절차·점검기·골격 전부 | 모듈별 DDIC 캐시 축적 |
| 인원 확산 | 같은 팀의 다른 담당자 | 저장소 전체 | 없음 (Cursor로 열면 규칙 자동 적용) |
| 유형 확산 | Module Pool·Enhancement·Interface·Batch·Forms | 요구사항 템플릿 5종 보유 | 유형별 코드 골격 추가 |
| 부문 확산 | 타 부문 SAP 개발 조직 | 규칙·절차·점검기 | 부문별 네이밍·패키지·권한 규칙 교체 |
| 도구 확산 | Cursor 미사용 조직 | 규칙 전문 + 프롬프트 조각 | 해당 도구에 지침 등록 |

확산이 쉬운 이유는 **사내 고유 정보가 몇 개 파일에 격리**되어 있다는 점입니다. 교체 대상은
`context/system-context.template.md`(릴리스·패키지·네이밍), `context/ddic-cache.md`(모듈별 DDIC),
`practice/error-patterns.md`(조직 경험) 세 곳이며, 규칙·절차·점검기·골격은 그대로 쓸 수 있습니다.

**SAP 외 영역으로의 이식** — "AI가 직접 실행할 수 없고 사람이 결과를 옮겨야 하는" 업무라면 동일
설계가 적용됩니다. 게이트로 승인받고, 출력 계약을 고정하고, 실패를 패턴으로 승격하는 구조는
업무 도메인과 무관합니다.

### 5.2 향후 계획

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1단계: 적용 건수 확대 | 조회성 리포트 중심으로 세션 누적, 모듈별 DDIC 캐시 확보 | 세션 5건 이상, 캐시 확정 행 축적 |
| 2단계: 측정 체계 확립 | 세션별 공수·재시도 횟수 기록을 `verify.md`에 표준 항목으로 추가 | 정량 효과 실측값 확보 |
| 3단계: 유형 확장 | Module Pool·Interface 등 확장 유형 코드 골격 추가 | 유형별 골격 + 점검 규칙 보강 |
| 4단계: 팀 확산 | 담당자 대상 적용 가이드 공유, 패턴 공동 축적 운영 | 다수 담당자 사용, 패턴 20건 이상 |
| 5단계: 점검 규칙 심화 | 운영 중 발생 오류를 규칙으로 승격, 성능 규칙 확대 | 규칙 25건 이상 |

**2단계를 우선 과제로 봅니다.** 현재 정량 효과를 저장소 근거로만 제시할 수 있는 이유는 공수 기록이
세션 산출물에 포함되지 않았기 때문입니다. `verify.md`에 단계별 소요 시간과 활성화 재시도 횟수를
표준 기록 항목으로 넣으면, 이후 세션부터 절감 효과가 자동으로 집계됩니다.
